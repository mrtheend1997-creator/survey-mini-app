# Долгая загрузка на Render: диагностика и варианты

Дата: 28.10.2026. Это диагностика и план. Инфраструктура не менялась, ничего не переносилось, платных действий не было.

## 1. Что проверено и как

| № | Что проверить | Результат | Как проверено |
|---|---|---|---|
| 1 | Тариф Render | В `render.yaml` у веб-сервиса и у базы стоит `plan: free`. Фактический тариф в панели Render я не видел, у меня нет к ней доступа | файл `render.yaml` |
| 2 | Причина холодного запуска | Бесплатный веб-сервис Render засыпает после ~15 минут без запросов. Первый запрос его будит, и пока он запускается, Render показывает экран «Application Loading». По документации Render это занимает до минуты. Совпадает с вашим описанием, но логи Render я не смотрел | документация Render о бесплатных сервисах + `render.yaml` |
| 3 | Время запуска backend | Само приложение после старта процесса отвечает за **~0,9 с** (локально, PostgreSQL 16). Основную часть ожидания на Render занимает подъём контейнера, а не наш код. Перед стартом выполняются миграции (`alembic upgrade head`), но это доли секунды, если новых миграций нет | замер локально |
| 4 | Скорость PostgreSQL | Локально запросы API отвечают за 1–2 мс. Скорость базы Render (Frankfurt) отсюда измерить нельзя | замер локально |
| 5 | Ресурсы | Бесплатный инстанс Render: 512 МБ RAM, 0,1 CPU (по прайсу Render). Этого мало для одновременной работы многих пользователей | прайс Render |
| 6 | Docker | Один контейнер: сборка frontend (node 20) и Python 3.12 slim с API. Конфигурация нормальная, на скорость пробуждения почти не влияет | `Dockerfile` |
| 7 | Размер frontend | Вся сборка **1,2 МБ**, главный JS 296 КБ (100 КБ gzip), графики грузятся отдельно только в админке | `npm run build` |
| 8 | Время ответа API | Локально 1–2 мс. На Render после пробуждения обычно быстро, холодный первый запрос долгий | замер локально |
| 9 | Логи | Логи Render я прочитать не могу. `fti-survey.onrender.com` недоступен из моей среды (прокси отклоняет соединение) | — |
| 10 | Автодеплой | В `render.yaml` автодеплой не отключён, то есть по умолчанию Render пересобирает сервис после каждого merge в `main` | `render.yaml` |

**Важный риск помимо скорости.** По правилам Render бесплатная база PostgreSQL временная: у неё ограниченный срок жизни (по документации около 30 дней), потом её нужно перевести на платный тариф, иначе данные пропадут. Проверьте в панели Render (раздел базы `fti-survey-db`), указана ли там дата истечения. Если указана, переход на платную базу срочнее, чем вопрос скорости.

## 3. Рекомендация

**Вариант А: остаться на Render и перейти на платные тарифы Starter (веб-сервис) и Basic (PostgreSQL).**

* Устраняет засыпание: экран «Application Loading» больше не появляется (это свойство платных тарифов Render).
* База становится постоянной, с ежедневными бэкапами.
* Ничего не переносится: тот же адрес, тот же URL в BotFather, те же переменные окружения и секреты.
* Около $14 в месяц.

Если важна цена или хранение данных в Узбекистане, следующий по порядку вариант Б: VPS с `docker-compose.yml`, который уже есть в репозитории.

Перед переходом на платный тариф нужно ваше подтверждение: я сам его не включаю.

## 4. Как перейти на Render без переноса (вариант А)

1. Сначала сделайте бэкап базы (раздел 5).
2. Render → база `fti-survey-db` → **Upgrade** → Basic. Данные остаются.
3. Render → сервис `fti-survey` → Settings → **Instance Type** → Starter.
4. Откройте Mini App через несколько часов простоя: экрана «Application Loading» быть не должно.
5. В `render.yaml` поменяйте `plan: free` на `starter` (сервис) и `basic-256mb` (база), чтобы Blueprint не вернул бесплатный тариф. Это можно сделать отдельным PR после перехода.

## 5. Если всё же понадобится перенос (вариант Б)

**Резервная копия перед любыми изменениями**

```bash
# адрес External Database URL из панели Render (раздел базы → Connect)
pg_dump --no-owner --format=custom "$RENDER_EXTERNAL_DATABASE_URL" -f fti_$(date +%F).dump
```

Храните дамп в двух местах. Загруженные файлы (логотип, картинки, файлы ответов) хранятся в PostgreSQL, поэтому попадают в этот же дамп.

**Подготовка нового сервера**

1. `git clone` репозитория, `cp .env.example .env`, заполнить: `BOT_TOKEN` (тот же, не менять), `SUPER_ADMIN_TELEGRAM_IDS`, `WEBAPP_URL` (новый https-адрес), `POSTGRES_PASSWORD`.
2. `docker compose up -d db`, затем восстановить данные:
   `docker compose exec -T db pg_restore --no-owner -U fti -d fti_survey < fti_ДАТА.dump`
3. `docker compose up -d`. Миграции применяются сами при старте API.
4. Проверить на новом адресе: `/api/health`, вход Super Admin, список опросов, число ответов совпадает с Render.

**Переключение без потери данных**

1. Выбрать спокойное время, поставить активные опросы на паузу.
2. Сделать финальный дамп с Render, восстановить его на новом сервере (шаг 2 выше).
3. В BotFather → Bot Settings → Menu Button / Web App URL указать новый адрес. Webhook новый сервер регистрирует сам при старте; если бот работает в режиме long polling (контейнер `bot`), на Render нужно выключить `TELEGRAM_WEBHOOK`, иначе Telegram будет слать обновления туда.
4. Проверить /start, открытие Mini App на телефоне и компьютере, отправку ответа.
5. Сервис и базу на Render не удалять минимум 2 недели: это точка отката (вернуть URL в BotFather).

**Откат:** вернуть старый Web App URL в BotFather и включить webhook на Render. Ответы, пришедшие на новый сервер после переключения, нужно перенести вручную, поэтому откат лучше делать в первые часы.
